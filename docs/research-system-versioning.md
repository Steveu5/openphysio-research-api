# Research system versioning

OpenPhysio exposes explicit versions for the evidence-search pipeline so ranking changes can be audited and compared over time.

## Version fields

- `algorithm_version`: overall search and prioritization behavior.
- `ranking_version`: article ordering and reading-priority logic.
- `evidence_scoring_version`: intrinsic article-quality scoring.
- `condition_dictionary_version`: condition aliases and competing-condition logic.
- `benchmark_version`: deterministic benchmark case set and metric contract.
- `result_snapshot_version`: immutable historical result snapshot format.
- `prompts.*`: version of each production prompt used for intent parsing, guided research answers, clinical chat, and clinical takeaways.

The active values and ranking configuration are centralized in `src/config/researchSystemVersion.js`.

## Runtime visibility

- `GET /health` includes `research_system` metadata.
- `GET /research/version` returns only the research-system metadata.
- Every HTTP response includes `X-OpenPhysio-Algorithm-Version` and `X-OpenPhysio-Ranking-Version` headers.
- Every `POST /research/search` response includes `researchSystem`, including cache hits.

## Persisted search provenance

Each new row in `research_search_queries` stores the full version snapshot under `parsed_query._openphysio_system`. This uses the existing JSON field, so no database migration is required.

The snapshot includes the algorithm, ranking, evidence-scoring, condition-dictionary, benchmark, prompt, weight, and penalty versions/configuration that were active when the search was executed. Historical search results remain linked to that query through `research_search_results.query_id`.

Cached records also store the same provenance in `parsed_query` and `response_json.researchSystem`. Query hashes are salted with the active research-system versions, preventing a result generated by an older ranking or prompt version from being reused after a release.

## Immutable result snapshots

Every completed search stores a compact immutable copy of the ranked article state under `parsed_query._openphysio_result_snapshot`. The snapshot contains the article metadata and ranking outputs required for historical inspection and current-version re-ranking, but deliberately excludes large source payloads such as `raw_metadata`.

Each snapshot includes:

- a snapshot format version;
- capture time and source (`live_search` or `cache_hit`);
- original rank positions;
- article identifiers and scientific metadata;
- evidence, relevance, and reading-priority scores;
- ranking explanations and appraisal flags;
- a SHA-256 checksum over the ranked snapshot payload.

The audit endpoint verifies the checksum before using the snapshot. If integrity verification fails or a legacy search has no snapshot, the audit safely falls back to the current `research_articles` records and clearly reports reduced reproducibility.

Searches served from cache are now recorded in history as independent user searches and receive their own result snapshot. This closes the previous gap where cache hits could be returned without creating an auditable history item.

A valid snapshot supports exact reconstruction of the historical article state and ranking outputs. Current-version comparison still applies the currently deployed ranking implementation; OpenPhysio does not claim to execute an archived copy of the old algorithm code.

## Benchmark reports

Generate a versioned report:

```bash
BENCHMARK_REPORT_PATH=artifacts/ranking-benchmark.json npm run benchmark:ranking
```

Compare a candidate against an approved baseline:

```bash
npm run benchmark:compare -- benchmarks/baselines/ranking-v1.json artifacts/ranking-benchmark.json
```

No baseline JSON should be committed until it has been generated by the benchmark command and reviewed. The comparator fails when the candidate breaks benchmark thresholds or regresses beyond the configured tolerances.

## Version bump policy

- Patch: implementation fix without intended ranking behavior change.
- Minor: backward-compatible scoring, prompt, dictionary, snapshot, or benchmark improvement.
- Major: incompatible metric contract, response semantics, snapshot format, or ranking behavior.

A change to weights, penalties, evidence rules, condition aliases, prompts, snapshot format, or benchmark cases must update the corresponding version. A behavior-changing release should also update `algorithm_version`.
